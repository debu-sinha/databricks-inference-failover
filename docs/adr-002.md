# ADR 002: Keep regional routing behind one shared API

Status: proposed integration, not deployed or validated

## Requirement

Applications should call one API for the same approved model and version. Routing across approved Databricks workspace entrypoints should be managed centrally. An application should not have to import a failover library just to select a backup region.

## Decision

Evaluate the existing shared gateway first. Azure API Management provides backend pools, priorities and circuit breakers. Determine whether its policies can meet the API, authentication, replay and recovery requirements before adding another runtime. This is a design option, not a tested Databricks integration. [APIM backends](https://learn.microsoft.com/en-us/azure/api-management/backends).

If a custom Python backend is needed, it can use this repository's client as one component. It would still need a shared HTTP API, caller authentication, model mapping, admission controls, concurrency limits, deployment and monitoring. The library does not run inside APIM policies. A second gateway is not required by the library.

For the PT design, prepare a model service and its PT endpoint in each regional metastore. The shared routing layer switches between workspace entrypoints. Do not depend on one model service referencing PT destinations across those metastores. Azure Databricks metastores are regional. [Metastore setup](https://learn.microsoft.com/en-us/azure/databricks/data-governance/unity-catalog/create-metastore).

Hosted PPT needs a separate placement assessment. Two workspace entrypoints do not prove independent physical inference capacity. The serving mode must be supported for the exact model, and permitted processing locations must be confirmed. [Model processing locations](https://learn.microsoft.com/en-us/azure/databricks/machine-learning/foundation-model-apis/compliance).

## Why this revision changes documentation first

The current synchronous client has a tested request interface and explicit failure policy. It has no HTTP server, caller-authentication layer, persistent circuit breaker or deployment. Reframing it as a complete shared gateway would overstate what exists.

Adding a web wrapper without an agreed API, identity model, hosting plan and live integration environment would not close the deployment gap. This revision therefore describes the intended architecture and responsibilities without adding an untested service. The existing validation record remains unchanged.

## Alternatives

| Option | Assessment |
| --- | --- |
| Existing gateway owns routing | First option to evaluate. Keeps policy in one place and may avoid a new service |
| Shared Python backend uses this client | Use if the selected gateway cannot meet the required behavior. Adds a runtime that must be secured, operated and tested |
| Every application imports the client | Supported client pattern, but does not satisfy the central-routing requirement by itself |
| Native destination fallback inside one model service | Useful within its supported configuration. Separate from customer-managed switching between regional workspace entrypoints |

## Acceptance before implementation is called complete

The selected integration must prove both model routes, the same approved model/version, route-specific identity and renewal, caller authorization, safe replay, expected load, both routes failing and controlled restoration. The shared entrypoint and its dependencies must survive the agreed failure too.

APIM backend priority selection and circuit breakers are not equivalent to the client's per-request policy. Native Unity Gateway destination attempts can add another retry layer. Choose the retry owner and calculate the combined attempts, cost and latency. [Gateway fallback](https://learn.microsoft.com/en-us/azure/databricks/ai-gateway/configure-traffic-splitting).

Gateway availability needs its own deployment decision. APIM's multi-region gateway configuration has tier and network requirements. It does not automatically create regional model backends. [APIM multi-region deployment](https://learn.microsoft.com/en-us/azure/api-management/api-management-howto-deploy-multi-region).

See [acceptance](acceptance.md) and [validation](validation.md). ADR 002 changes the target integration, while [ADR 001](adr-001.md) remains the record of the shipped client's behavior. No production deployment or new integration-test result is claimed by this decision.
